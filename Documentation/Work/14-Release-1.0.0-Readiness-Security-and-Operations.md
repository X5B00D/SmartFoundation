# حالة الإصدار 1.0.0 والأمن والتشغيل

تاريخ التحديث: 2026-09-05.

## الغرض وحدود الادعاء

يوثق هذا الفصل الحالة الحالية المثبتة للإصدار 1.0.0 بعد اكتمال أنشطة التحقق السابقة للتسليم. وهو ملحق تقني للوثيقة الشاملة، وليس شهادة أمنية أو اعتماد إنتاج نهائي. تنطبق النتائج على الإصدار والنطاق والبيئة وقت التحقق، وتبقى اختبارات القبول التشغيلي بعد النشر مرتبطة ببيئة الاستضافة الفعلية.

ترتيب الثقة المستخدم هو: الكود وملفات المشروع الحالية، ثم أدلة التحقق النهائية، ثم وثيقة التسليم المعتمدة، ثم التوثيق التاريخي. لا تتضمن الوثيقة أسرار اتصال أو كلمات مرور أو بيانات مستخدمين فعلية.

## Interactive Application Security Testing

تعذر تنفيذ Interactive Application Security Testing داخل نطاق تحقق فريق التطوير بسبب عدم توفر أداة مجانية أو مفتوحة المصدر مناسبة تدعم البيئة التقنية للتطبيق وتحقق مستوى الاختبار المطلوب. لا تسجل نتيجة IAST على أنها PASS أو COMPLETED.

ينفذ الاختبار من الجهة المختصة أو من تكلفه بذلك ضمن إجراءات التحقق والقبول قبل الاستضافة النهائية. إذا نتج عنه Finding أو Vulnerability، يتولى فريق التطوير المعالجة ثم إعادة التحقق قبل الاعتماد النهائي.

## مكونات الطرف الثالث والتراخيص

تمت مراجعة مكونات الطرف الثالث والتبعيات المستخدمة ضمن نطاق الإصدار، بما في ذلك التراخيص المرتبطة بها، ولم تظهر ضمن نطاق المراجعة الحالية ملاحظات معروفة تمنع استخدامها في الإصدار محل التسليم، مع مراعاة شروط الترخيص الخاصة بكل مكون. يحتفظ SBOM بالجرد التفصيلي للمكونات والتبعيات. هذه مراجعة فنية ضمن نطاق الإصدار وليست رأيًا قانونيًا أو إقرارًا بأن المكونات غير مقيدة.

## المصادقة والترخيص والجلسات الحالية

يستخدم التطبيق Cookie Authentication مع Claims بعد نجاح التحقق من بيانات الدخول عبر مسار DATACORE. كما يحتفظ بسياق المستخدم التشغيلي في Session. يسجل التطبيق Authentication وAuthorization، ثم يطبق SessionGuardMiddleware لمقارنة هوية Cookie/Claims مع Session وإغلاق الوصول عند فقد السياق أو عدم التطابق.

ترتيب middleware ذي الصلة في الكود الحالي هو:

`Routing -> Session -> Authentication -> Authorization -> SessionGuardMiddleware -> Endpoints`

الحالة التاريخية التي لم يكن فيها Cookie Authentication أو Claims أو SessionGuard مسجلًا محفوظة في سجل الفجوات، لكنها لا تمثل Current State للإصدار 1.0.0.

## معمارية Session والتوسع

النموذج التشغيلي الحالي هو Single Application Server. يستخدم التطبيق AddDistributedMemoryCache وAddSession، لكن التخزين الفعلي للجلسة process-local/in-memory، وهو مناسب للنموذج الحالي المعتمد. لا يصنف ذلك تلقائيًا كثغرة أمنية مفتوحة.

عند الانتقال إلى عدة خوادم أو instances أو Load Balancer أو High Availability يجب إعادة تقييم Distributed Session Storage، ومفاتيح Data Protection المشتركة، وSession Affinity عند الحاجة، وLoad Balancing، وShared Storage للملفات اللازمة، وHealth Checks، وCentralized Monitoring. لا يوجد في الكود الحالي دليل على تنفيذ هذا التصميم متعدد الخوادم.

## Content Security Policy

CSP مطبقة وفعالة ضمن التطبيق. تعتمد بعض مكونات الواجهة الحالية، ومنها نمط Alpine.js المستخدم، على إعدادات توافق لازمة للتشغيل. سجل القرار الحالي ذلك كقرار توافق معماري مقبول ضمن البنية الحالية وليس كثغرة مفتوحة بذاته.

تعاد مراجعة السياسة عند تغيير Alpine.js أو مكتبات الواجهة، أو إعادة تصميم JavaScript، أو توفر إمكانية تطبيق سياسة أكثر صرامة دون كسر الوظائف، أو ظهور دليل أمني جديد.

## Application Logging

يستخدم التطبيق ILogger والسجلات التشغيلية وسجلات AuditLog وErrorLog المرتبطة بقاعدة البيانات بحسب المسار. الضوابط التشغيلية المطلوبة هي عدم تسجيل كلمات المرور أو بيانات Session أو المعلومات الحساسة دون حاجة، وحماية ملفات السجل من التعديل والوصول غير المصرح، وتطبيق Log Rotation وRetention وفق سياسة الجهة، ومزامنة الوقت، وإتاحة السجلات للمخولين أثناء التحقيق، ومراقبة الأنماط والأخطاء المتكررة.

Application Logging مسؤولية مشتركة بين التطبيق والتشغيل. أما SIEM أو Centralized Logging وتجميع IIS وWindows وSQL والتطبيق مركزيًا فهي قدرة في بنية الاستضافة، ولم يثبت تنفيذها من كود التطبيق؛ تعتمد على قرار الجهة المستضيفة.

## قاعدة البيانات وSQL Server

يبقى DATACORE اسم قاعدة البيانات التشغيلية الموثقة، وكانت DATACORE الحية مصدر الحقيقة في المصالحات السابقة الموثقة. استخدمت البيئة المرجعية SQL Server 2019 لأعمال التطوير والتحقق. لا تمثل SQL Server 2019 Developer Edition متطلبًا للإنتاج؛ تستخدم بيئة الإنتاج إصدار SQL Server مدعومًا وEdition مرخصة ومناسبة وفق سياسات الجهة المستضيفة.

الاتصال الموثق في البيئة المرجعية يستخدم Windows Integrated Security. لا تعرض الوثيقة قيمة Connection String أو هوية الخدمة.

## النسخ الاحتياطي والاستعادة

النموذج التشغيلي يشمل Full Backup وDifferential Backup وTransaction Log Backup وRestore Drill. الأهداف التشغيلية المستهدفة هي RPO = 15 minutes وRTO = 1 hour. هذه أهداف وليست ضمانات تتحقق تلقائيًا.

يعتمد تحقيقها على Production Backup Policy، وجدول Transaction Log Backup، وسعة وموقع التخزين، والمراقبة والتنبيه، وسلامة سلسلة النسخ، واختبارات الاستعادة الدورية، وخصائص بيئة الاستضافة. FULL Recovery Model موثق للبيئة المرجعية؛ يجب التحقق من ملاءمة إعداد الإنتاج مع جدول Log Backup والأهداف المعتمدة.

## اعتبارات الاستضافة على IIS

### معمارية التطبيق الحالية

التطبيق ASP.NET Core MVC على .NET 8 ومهيأ للعمل خلف IIS/ASP.NET Core Module. لا تثبت ملفات المصدر وحدها إعداد خادم إنتاج بعينه.

### توصيات الاستضافة

- Windows Server بإصدار مدعوم وIIS مع ASP.NET Core Hosting Bundle for .NET 8.
- Application Pool مخصص وهوية خدمة مخصصة محدودة الصلاحيات وفق Least Privilege.
- HTTPS وشهادة TLS موثوقة وإعدادات Firewall وBindings معتمدة.
- صلاحيات ملفات تقتصر على مسارات التشغيل والرفع والسجلات اللازمة.
- تفعيل IIS Logs وRetention المناسب، ومنع Detailed Errors عن المستخدمين في الإنتاج.
- حماية الإعدادات والأسرار خارج المصدر ومراقبة صلاحية الشهادة والموارد.

### القبول بعد النشر

يتحقق فريق الاستضافة من بدء الموقع، والاتصال بـDATACORE، وHTTPS/TLS، والمصادقة والجلسة والصلاحيات، والوظائف الحرجة، وIIS/Application Logs، والنسخ الأولي والاستعادة، والمراقبة والتنبيه. لا تسجل جاهزية الوثيقة بوصفها Final Production Approval.
